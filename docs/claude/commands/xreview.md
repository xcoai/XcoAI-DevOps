# /xreview — 代码审查

审查范围参数：$ARGUMENTS（为空时审查工作区全部未提交改动）

## 上下文（自动注入，仅轻量概览）

当前状态：
!`git status --short`

改动概览：
!`git diff HEAD --stat`

## 你的约束

- **只审查，不修改文件。** 修复建议以 diff 片段形式给出，由用户决定是否采纳。
- **确定审查范围**：
  - 参数为空：审查工作区全部未提交改动（含已暂存与未暂存）。
  - 参数为路径或分支：以参数为准，自行用 `git diff` / `git show` 获取对应范围的改动；审查分支时用 `git merge-base` 确定与主干（main 或 master，用 `git branch` / `git rev-parse` 确认）的分叉点，命令失败时如实说明，不要静默回退。
  - 上方自动注入的只是概览；全量 diff 由你按需获取，不要依赖注入内容做结论。
- **`git diff` 不含未跟踪的新文件**：`git status` 中标记 `??` 的文件必须用 Read 逐个读取并纳入审查，不得遗漏。
- 若 diff 超过约 800 行，先按文件列出清单，询问用户优先审查哪些，不要囫囵吞枣。
- 只报告你能在代码中指出具体位置的问题，**每条必须带 `文件:行号`**。不确定的写在"需人工确认"，不要升级为 Blocker。
- 不编造问题凑数。某一级别没有发现就写"无"。
- 审查时读取被改动文件的完整内容及其直接调用方，不要只看 diff 片段。
- 若项目存在 `docs/review-checklist.md`，读取并把其中的检查项一并纳入（项目扩展点）。

## 检查维度（对应全局 CLAUDE.md）

1. **安全（第 4 节，任何命中即 Blocker）**：硬编码密钥、SQL/命令拼接、缺失鉴权或越权、弱哈希、关闭 TLS 校验、PII 明文、可疑依赖。
2. **正确性**：逻辑错误、边界条件、并发问题、错误处理（吞异常、丢上下文）、资源泄漏。
3. **架构（第 3 节）**：分层越界、实体直接暴露、API 破坏性变更未版本化、迁移脚本不兼容、缓存无失效策略、N+1、缺超时/重试/幂等。
4. **测试（第 6 节）**：新逻辑是否有测试、测试是否有有效断言、是否依赖时间/顺序/外部服务、是否有被跳过或删除的测试。
5. **变更卫生**：是否包含任务无关改动、是否有抑制注释（`eslint-disable` / `# noqa` / `@ts-ignore`）、依赖或锁文件是否被意外修改、是否有调试残留（`console.log`、`print`、`TODO` 无人认领）。
6. **文档与契约**：API 改动是否同步 OpenAPI/proto；README/ADR 是否需要更新。

## 严重度定义（与全局 CLAUDE.md 第 8 节一致）

| 级别 | 编号 | 定义 | 对合并的影响 |
|------|------|------|--------------|
| **Blocker** | B1, B2… | 安全红线、数据丢失/损坏风险、明确的正确性错误 | 必须修复才能合并 |
| **Major** | M1, M2… | 架构违规、性能问题、缺失测试、破坏性变更未版本化 | 应在本 MR 修复，例外需说明 |
| **Minor** | L1, L2… | 可维护性、错误处理不完善、命名/结构问题 | 建议修复，可跟进 |
| **Nit** | N1, N2… | 风格、注释、微小可读性改进 | 可选；最多列 5 条 |

## 输出格式（严格按此结构）

### 结论
**[可合并 / 修复后可合并 / 阻塞]** — Blocker N · Major N · Minor N · Nit N
一到两句话概括改动质量与主要关注点。

### Blocker
#### B1. <标题>
- 位置：`path/file.ext:42`
- 问题：具体描述，说明触发条件与后果
- 依据：全局 CLAUDE.md 第 x 节 / 项目 checklist 第 y 条
- 建议：
  ```diff
  - 问题代码
  + 修复代码
  ```

### Major
（同上格式，编号 M1, M2…）

### Minor
（同上格式，编号 L1, L2…；可省略 diff；超过 10 条时归纳共性模式，不逐条罗列）

### Nit
（一行一条，编号 N1…，最多 5 条）

### 需人工确认
你无法从代码判断、需要业务或运维背景的疑点。

### 做得好的地方
1–3 条，具体到位置。审查不是只挑刺，也用于让好的模式被复用。
